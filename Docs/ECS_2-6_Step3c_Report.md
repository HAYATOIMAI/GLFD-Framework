## 0. 結論

- ユーザーの見込み「**3% 程度の差を追ってソースを変えるのは、今の測り方では確かめられない**」を、数字で確かめた。
- 同じ exe を 2 つ並べた A/A では、**交互に 4 ブロックずつ並べた X と Y の差は 1.1% で、範囲が重なる。** 3a の A/B で見た「4 ブロックすべてで約 3% 高く、範囲が重ならない」形は、同じ exe では出なかった。
- 一方、**1 ブロックずつ見ると、同じ exe でも CollisionSystem は最大 4.0% 動く。**
- さらに w の掃引(3b)で、**3a と同じ「参照で持つ」コードの CollisionSystem を持つ 3b のビルドは、変更前と同程度(313.8〜318.1 µs)だった。**
- → 3a の +3% は、回やブロックの揺れよりも、**ビルドの違い(他のファイルの変更でコードの配置が変わること)による可能性が高い【推測】。** 「参照で持つ形が CollisionSystem を遅くした」という見立ては**支持されない。**
- 局所変数に写す変更も、それ自体が配置を変えるので、効果と配置の揺れを区別できない(ユーザーの分かれ目 2)。**変更は入れない。**

| 3b の掃引 | 3a(参照で持つ、20 本) | 325.8 µs | — |

- 3b は、CollisionSystem の本体も本数(20 本)も 3a と同じ。違うのは他のファイル(`ParallelFor.h` の `GrainFor`、他のシステムの粒度)だけ。
- それでも 3b のビルドは 3a より 3% 程度低く、変更前と同程度だった。
- **同じ処理でも、ビルドによって 3% 程度動く**と読むのが自然【推測】。確かめるには、配置を固定する手段(関数の整列など)か、多数のビルドでの分布が要り、今の測り方の外にある。

### 5.1 ユーザーが記録した事項(2-6)

- **部品だけを測ると、実際の組み合わせでの取り合いを過小に見積もる。** 手順1 の `Push`(単独 0.021 µs / 本物で 0.098 µs)と、3a の Hit(確保 3 回分の見積もりより大きく、37.5 → 15.8 µs)。
- `std::function` の除去は、理由だった確保が 3a で解消したので優先度を下げた。将来 `KickJob` に大きな取り込みを直接渡すと確保が戻る危険は、根の probe(`probe_root_job_dispatch`)が押さえている。
- w = 16 µs は、同じ時間で使うコアが少なかった(large で 1.57 と 2.21)。**CPU の予算が問題になったら w を上げる候補**として、`ParallelFor.h` のコメントに残した。
- 計測のスクリプトで、記録の値を回ごとに作り直していなかった件は 2 度目(2-5 の探索、3b の掃引)。**以後、最初から回ごとに作り直す形で書く**(3c の `aa.ps1` はその形)。
